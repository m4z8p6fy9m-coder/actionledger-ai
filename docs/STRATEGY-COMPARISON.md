# Comparing recovery strategies

These scenarios compare narrowly defined local simulations, not whole products. All amounts are simulated. The provider and ledger use separate SQLite stores, and lab workers are separate processes. The seeded lab fixes payloads and case order, not operating-system scheduling or generated IDs. Run:

```sh
pnpm lab --seed 5409 --output evidence.json
pnpm evidence:verify evidence.json
pnpm demo:multi-agent
pnpm exec vitest run tests/ledger.test.ts packages/runtime/test/runtime.test.ts
```

`--output` must name a new file. The lab records actual and expected checks and exits unsuccessfully on a mismatch. The verifier checks consistency and the digest, not authenticity. The [recorded local lab result](evidence/strategy-comparison-5409.json) has 8/8 scenarios and 36/36 checks passing on Windows x64, Node 24.19.0, seed 5409; it is one run, not an independent audit.

| Expired provider key        | A retry can create another effect if the provider no longer recognizes its key.                                                                        | Protection lasts only within the provider's actual contract and retention.                                                      | The local simulator retains keys indefinitely; an expiry fault is **not tested** in this lab. Do not infer safe replay after provider key expiry. The separate enterprise runtime reconciles UNKNOWN by reads and never automatically re-dispatches it. |

The dashboard ledger and enterprise runtime are separate implementations with different recovery policies. The dashboard permits explicit recovery of UNKNOWN only for its idempotent simulator; the enterprise runtime never automatically re-executes UNKNOWN. Neither implementation can guarantee exactly-once effects solely through a local database. Direct external calls bypass the ledger and guard. See [security review](SECURITY-REVIEW.md) for trust boundaries and open work.
